# 构建记录：从服务导航到「万点飞花」

「万点飞花」最初要解决的是一个具体问题：打开一个公网入口，用密码和手机 Authenticator 的六位动态码登录，然后像使用电脑一样，在桌面窗口里打开和管理自己的集群项目。IPv4 由 `edge-v4` 承接，IPv6 由 `core-v6` 承接，两条路径进入相同的身份与应用边界。

这里的 Web OS 指浏览器里的统一工作环境：桌面、应用启动器、多窗口、节点视图、文件与任务入口。它的价值最终取决于真实项目能否完成工作，而不只取决于界面是否像操作系统。

本文是脱敏后的实施复盘。公开材料保存设计取舍、验证方法和失败教训；私有桌面实现、部署包、身份数据和现场信息另行维护。本仓库不应被理解为已经包含完整应用源码或一键部署产品。

## 第一版偏离了问题

最早的界面更像一张集群仪表盘：卡片、指标、节点状态占据了中心。用户明确指出它既不好看，也没有满足“虚拟电脑桌面”的要求。这个反馈暴露了需求理解上的偏差：把所有服务摆在一页，并不会自动形成桌面。

后续工作才围绕实际操作展开：项目成为可启动的应用；窗口能够切换焦点、移动、调整大小、最小化与恢复；桌面和启动器承担应用入口；节点、文件、任务作为有明确能力边界的工具进入同一界面。参考 macOS 的菜单栏、Dock 和窗口层次，是为了形成一致的交互，而不是把所有内容重新包装成更多卡片。

这次调整应当发生得更早。先验证“打开应用、并排操作、切换回来”的关键路径，会比先堆积监控面板更接近用户的原始目标。

## 接入真实项目后，验证标准必须改变

本地演示能证明窗口系统和页面交互。它不能证明集群里的真实项目已经接入。接入时曾出现另一个误判：探测地址返回 HTTP 200，便容易被当作“面板已经可用”。实际上，返回成功的可能只是提示页、默认页、登录页或健康检查。

后续验证改为从桌面窗口打开真实页面，检查页面身份、跳转目标、资源加载与交互。MCSManager、NetAlertX、Zashboard 和 Harness 的真实页面曾在窗口内打开验证。这些证据说明浏览器已经到达相应页面，不能据此宣布所有原站登录、管理动作、下载和长连接均已完成验收。

项目注册也因此需要固定来源、固定入口和明确的可用状态。一个应用处于“可探测”“可打开登录页”“已完成授权管理验收”，应当在记录里有所区别。

## MCSManager 让“一个网页”变成了多条协议链路

MCSManager 是接入过程中最有代表性的例子。面板登录页能够显示，实例终端和文件功能仍可能不可用，因为浏览器还需要连接 daemon。官方反向代理说明也明确区分面板与 daemon，并提醒上传、下载和控制台需要后者的 HTTPS/WebSocket 路径。[MCSManager 官方说明](https://docs.mcsmanager.com/ops/proxy_https.html)

因此，工作从“给面板套一个窗口”扩展为梳理浏览器实际发出的请求：面板、daemon、WebSocket、分片传输与浏览器端地址映射。候选方案使用固定的同来源分流，原站的控制器凭据和实例权限继续保留。浏览器端映射与经过授权的实际管理操作仍需要应用所有者逐项验收。

这也适用于其他项目：统一桌面的登录不等于自动获得所有原站权限；反向代理成功也不等于原站支持嵌入。嵌入策略、Cookie、原站身份与协议来源必须分别处理。

## 生产身份与本地身份分开实现

本地原型先提供密码与 TOTP 交互，帮助验证桌面登录体验。生产路线随后明确为 Authelia 双因素入口与 OIDC 后端会话，限定唯一所有者。生产后端关闭演示登录和预览入口，不能把本地演示会话作为公网身份的替代物。

已有的密码哈希和 Authenticator 绑定由所有者本人通过受控迁移流程保留，避免无必要地重新设置密码或扫描二维码。真实身份材料没有进入公开仓库。

身份统一以后仍有未完成的部分：平台会话退出、身份门户退出、原应用会话退出，以及已建立的 WebSocket/SSE 连接终止，需要分别验证。删除平台 Cookie 不能直接作为“全部应用已退出”的证据。

## 安全部署工具也制造了操作负担

部署中逐步补上了固定版本、文件来源核对、服务账户、严格权限、失败回滚、证书成对安装和不自动启用公网等边界。这些约束有实际作用，也让工具数量不断增加。用户需要在本地终端与服务器之间反复切换，复制多条命令，再把结果带回来。

这段经历并不顺畅。阶段拆分过细、通用错误缺少定位信息，以及后续修复入口层层增加，都扩大了操作成本。安全与可操作性需要一起设计：成熟的准备阶段应当合并为一次本人 `sudo` 执行，内部仍逐项核对、保存可恢复状态并显示阶段结果。合并执行不应悄悄变成启动服务或修改 DNS。

过程中还修复了两类此前未被合成测试覆盖的真实环境问题：Windows PowerShell 找到多个 SSH 程序，导致调用路径变成数组；Python 在真实终端上以读写模式打开 TTY，触发流操作异常。两者都说明测试替身不能替代运行环境本身，详见[故障手册](05-troubleshooting.md)。

## 证书失败需要协议证据

一次 ACME 演练在用户输入完成后失败。早期仅有通用拒绝，无法判断失败发生在输入、文件准备还是证书客户端阶段。随后增加本机诊断，输出固定分类，保留私有日志在服务器内。

进一步证据显示，最后相关响应是 HTTP 503，并带有 `rateLimited` 类型。它不能被直接归因为用户输错 Token。处理方式是保留专用账号和凭据、读取 `Retry-After`、到期后只允许一次显式恢复，而不是删除现场并不断重新初始化。演练恢复和之后的生产签发最终通过；具体故障处理见[故障手册](05-troubleshooting.md#acme-返回-503-或-ratelimited)。

## 在另一台机器验证通过，仍漏掉了版本问题

这是生产准备中一个本可更早发现的失误：配置曾在另一台机器的较新 Caddy 上验证，而 `core-v6` 上为新 Web OS 准备的独立 Caddy 实际仍是 2.6.2，无法接受所用的代理信任配置。

修复仅针对新 Web OS 的独立可执行文件，将它升级至经过来源核对的 2.11.7，保留旧文件与回滚能力，没有接管其他应用的网关。验证也从一个笼统的失败结果改为四个独立阶段：生产后端、公开证书、Authelia、Caddy。原始输出在本机内存中分类，只显示固定的安全结果。

最新的本人执行结果是：独立网关已升级，四个生产校验阶段均通过。这个结果是配置准备的进展，尚未完成发布选择、服务启动、生产入口重载、DNS 切换或真正公网验收。

## 当前进度怎样表述才准确

| 层级 | 已有证据 | 仍不能据此推导的结论 |
| --- | --- | --- |
| 本地演示 | 桌面、窗口、应用入口和本地登录交互可运行 | 已连接所有集群管理能力 |
| 真实应用窗口 | 多个真实项目页面已在窗口中打开验证 | 所有原站操作、长连接和文件传输均可用 |
| 生产配置校验 | 生产后端、证书、Authelia、Caddy 四阶段通过 | 已启动公网服务或完成双栈访问 |
| 公网验收 | 尚待执行 | 密码与 TOTP、应用管理及退出链路已全部闭环 |

文件、任务与节点界面还不能被描述为完整的生产控制面。远程读写、任务执行、权限约束、审计和失败恢复，需要连接真实后端并单独验收。接下来的工作应继续服务于原始目标：登录后，在桌面窗口里完成真实集群工作，并明确告诉使用者每个应用已经能做什么。
