# 全屏、快捷键与右键菜单：把输入接回桌面

记录日期：2026-10-19。本文记录**已实现、正在完成本地验收的输入体验候选**，尚未生产激活。此前桌面、本人 MFA 解锁和真实应用页面的证据见[桌面体验与开机解锁](09-os-experience-and-unlock.md)；不能把此前结果算作本轮输入桥接已在生产四个项目中通过。

这轮目标是让同一个桌面命令在桌面和受管项目窗口中具有一致含义，同时保留文字编辑、原应用菜单和浏览器安全退出。本文公开原理、流程与验收边界，不包含私有实现源码、内部执行命令、生产地址或凭据。

## 全屏是一种显示状态

进入全屏由用户的明确操作发起，请求桌面文档进入 Fullscreen API 模式；全屏命令只负责进入，不将反复触发解释成来回切换。请求可能被拒绝，也可能在稍后才完成，因此界面需要同时表示“请求中”“已进入”“不支持”或“未允许”。用户激活与全屏状态的标准语义见 [WHATWG Fullscreen API](https://fullscreen.spec.whatwg.org/)。

Esc 用来退出网页全屏，**不发送桌面锁定或注销**。浏览器自己的全屏变化只同步状态、释放已有键盘锁，不自动重新申请锁。退出、请求失败、组件卸载或迟到的结果都要清理；用户已经要求退出时，迟到的进入结果也不能把桌面留在相反状态。

浏览器保留自己的安全退出机制，网页不能禁止它，也不能保证覆盖操作系统保留的组合键。浏览器菜单进入的全屏与网页请求的全屏还可能具有不同能力，不能只看窗口铺满屏幕就宣称增强快捷键可用。

## Keyboard Lock 是可失败的增强

候选先探测所需 API，再仅为桌面命令请求一组有限的物理键；不请求全部按键，也不请求 Esc。即使存在 API，实际调用仍可能拒绝。此时保持可用的界面按钮和明确提示，允许浏览器或宿主系统处理仍由它们保留的按键，不能把失败显示为“已接管键盘”。[Chrome 的 Keyboard Lock 说明](https://developer.chrome.com/docs/capabilities/web-apis/keyboard-lock)也将可用按键限制在宿主系统允许的范围内。

浏览器文档需要按日期核实。[Chrome 官方权限公告](https://developer.chrome.com/blog/keyboard-lock-pointer-lock-permission)在 **2026-03-17** 的更新中明确取消推出 Keyboard Lock 与 Pointer Lock 权限的计划。该页仍保留旧标题和旧段落，不能只凭搜索摘要或较早版本号写成“某版本起必弹权限框”。当前实现依据能力探测和调用的真实成功/拒绝结果，不把固定权限查询当作普遍前提。

本地内置浏览器实际拒绝了键盘锁申请，候选显示降级状态。这个结果只证明拒绝路径真实发生并得到处理，不能用来宣称全部按键、全部浏览器或系统组合键已经生效。

## 一套命令判定，两个输入位置

桌面容器与受管 iframe 使用同一个快捷键分类规则，避免两份键位表逐渐出现差异。规则先判断组合键与上下文，再决定是否消费事件：

- 输入法组合、AltGraph、重复事件或已经被页面处理的事件不应误触桌面命令。
- 文件应用的 Ctrl/Cmd＋N、S、F 分别进入新建、保存和搜索路径，继续使用原有授权与未保存保护。
- 原应用输入框和编辑器保留自己的编辑语义，不能把文字删除或保存操作误当作关闭窗口或系统写入。
- 无法交给桌面处理的按键保留浏览器行为，并提供菜单或按钮入口。

本地真实文件 API 沙盒已验证 Ctrl＋N、Ctrl＋S、Ctrl＋F。这里的“真实”指实际调用沙盒文件接口并检查结果，不代表本轮已经在生产目录或四个原站里完成同样操作。

## iframe 输入桥接只传递有限 UI 意图

浏览器不会把跨来源 iframe 的键盘事件自动冒泡给桌面。候选为固定受管的四个项目提供一个同源 UI 桥，子页面使用同一命令分类器，再通过受限消息把少量桌面意图交给父页面。普通自定义项目不会因此自动获得这项能力。

父页面逐项核验消息来源窗口、精确 origin，以及对应 iframe 是否仍连接、是否为当前活动且可见窗口；再核对消息形状和有限命令集合。发送方不能通过自报窗口 ID、任意 URL 或额外字段决定操作对象。跨来源消息应验证来源与内容的原则见 [HTML Standard 的消息安全说明](https://html.spec.whatwg.org/multipage/web-messaging.html#security-postmsg)。

桥接只传有限的窗口/搜索/显示意图或菜单坐标，不传文本字段内容、页面 URL、密码、令牌或其他秘密，也不提供锁定、注销、文件写入或远程命令能力。桌面自己的锁定按钮与受保护文件 API 继续走各自原有流程；输入桥不是新的认证或管理权限入口。

这里还要区分用户输入和程序合成事件：隔离浏览器检查使用实际可信键盘与右键事件；单独创建一个脚本事件不能代替该验证。后台窗口、已断开的 iframe、错误来源或不合格消息应被拒绝，即使消息看起来像一个有效命令。

## 右键菜单分清归属

统一外壳不应吞掉原应用的业务菜单。候选遵循三层归属：

| 位置 | 处理方向 | 必须保留的边界 |
| --- | --- | --- |
| 桌面、窗口与系统工具 | 将通用浏览器右键入口替换为对应的桌面菜单 | 菜单项连接实际 UI 命令，不放置没有后端的管理成功按钮 |
| 原应用已处理的右键事件 | 保留原站自己的业务菜单 | 已被原站处理的事件不再转换成桌面菜单；逐项目验证事件顺序 |
| 子页面文字编辑位置 | 使用页面内的本地编辑菜单 | 编辑目标和选区留在子页面，不经桥传给桌面；不支持的操作明确降级 |

子页面编辑菜单仍处于候选修正与补验阶段，不把它记为已通过。复制、剪切、粘贴等操作还受浏览器和用户手势限制，不能显示成功后假定剪贴板已改变，也不应为此后台读取或上传剪贴板。
