# 文档公开与更新流程

公开项目经历，既要让读者复用技术结论，也要保护个人部署信息。这个仓库采用独立目录、重新编写和干净Git历史发布，没有把私有运维工作区整体推送。

## 发布内容

保留产品目标、组件角色、公开协议、依赖验证版本、错误类型、排查思路和验收标准。用`core-v6`、`edge-v4`描述节点职责，用`example.net`与文档地址说明网络关系。版本不兼容等教训必须保留足够细节，不能脱敏成无法复现的空泛建议。

真实域名、地址、节点与SSH别名、账号邮箱、个人路径、发布编号、生产制品指纹和原始日志不进入公开稿。密码哈希、TOTP密钥与二维码、SMTP授权码、DNS Token、私钥、证书、会话和账号数据库也不进入仓库。截图和附件如不能证明已脱敏，就不发布。

## 一次发布的顺序

1. 在独立目录写公开稿，列出本次允许发布的文件；不沿用私有仓库的Git历史。
2. 先核对事实：配置校验、页面可达、本人业务操作和真正公网验收分别记录，尚未完成的目标写入路线图。
3. 检查正文、代码块、示例、链接、图和文件名。所有部署输入使用示例值，移除无法解释来源的日志或附件。
4. 自动扫描已知私有标识、非示例地址、邮箱、凭据格式和密钥材料；再由另一位审阅者检查语义与事实。扫描通过不能代替人工判断。
5. 只暂存已审查的文件，检查暂存差异与完整历史；提交身份使用公开名和GitHub提供的noreply地址，避免全局Git配置带入私人邮箱。
6. 发布后从远端读取提交、可见性和文件清单，核对推送结果与文档链接。

不要先推送再删除秘密；删除最新文件不会从已有Git历史中移除内容。若发现真实凭据泄露，应先处置凭据，再处理历史。

## 持续更新

每次实际推进后，先更新README状态表与ROADMAP，再更新对应教程。上线、恢复、注销、任务或应用管理只有完成实际验收才标记完成。新增经验仍走同一脱敏与Git审查流程，不把聊天记录或机器日志直接追加进来。

运维流程的简化也要有证据：把已经验证的同阶段步骤合并、保留预览与明确诊断，比不断要求操作者粘贴新的孤立命令更容易维护。
