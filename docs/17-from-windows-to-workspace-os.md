# 从窗口门户走向有连续状态的 Web OS

**状态：本轮工作空间能力已发布，已取得有限公网操作证据。** 应用生命周期、应用全屏与桌面空间、文件事务、通知专注和搜索深链接已完成实现与分项检查；发布后服务运行态复核通过，公网重载自动续接既有 SSO。隔离浏览器交互、Linux 文件系统检查和下文列出的公网验收分别记账，不能据此声称完整 macOS 或全部项目业务已经完成。

此前已发布的桌面升级补齐了默认在线监控视图与个人资料。主人使用密码和 Authenticator 解锁后，实际原生监控默认选中在线视图，真实读数持续变化，完整资产仍保留；头像保存后刷新整页仍能读取，并已验证恢复默认。相关操作与保存范围见[上一章](16-desktop-settings-and-interaction.md)。本章转向下一层问题：窗口能打开之后，如何让整套工作空间保持一致的状态和操作逻辑。

## 先把应用和窗口分开

如果应用只有“打开链接”和“关闭弹层”两种状态，程序坞、菜单栏、快捷键和多桌面很容易互相矛盾。例如，用户关闭了一个窗口，程序坞却无法说明应用是否仍在运行；最小化后按应用切换键，又找不到原来的页面。

本轮把应用会话与窗口状态分开保存：

| 操作 | 应用会话 | 窗口与页面 |
| --- | --- | --- |
| 打开或激活 | 进入运行集合，并更新最近使用顺序 | 找回已有窗口；需要时才创建窗口 |
| 最小化 | 继续运行 | 收起窗口，从程序坞恢复 |
| 隐藏应用 | 继续运行 | 暂时隐藏；再次激活时恢复 |
| 关闭窗口 | 应用会话可以保留 | 关闭对应窗口，先处理未保存内容 |
| 退出应用 | 从运行集合及切换顺序移除 | 关闭对应窗口，遵守未保存确认 |

这里的“运行”指 Web OS 的应用会话，不是远端服务的进程。退出一个管理窗口不会自动停止服务器上的项目，也不应成为重启容器或撤销账号的隐式命令。关闭窗口与退出应用分别具有含义，这一交互参考了 [Apple 的窗口与应用快捷键说明](https://support.apple.com/en-us/102650)。

最近使用顺序也需要稳定：开始切换应用时先取得一份顺序快照，再在快照内移动高亮；确认选中后才激活应用、更新顺序。否则每次移动高亮都会重排列表，下一次按键可能跳到不同目标。取消切换则应回到原焦点，不额外激活某个应用。

浏览器只保存有限的应用标识和排序。项目页面里的身份材料继续由服务端钥匙串与原站协议管理，应用列表不保存 Cookie、令牌或页面正文。

## 区分应用全屏、桌面空间和浏览器全屏

这三个动作解决不同问题：

- 应用全屏让一个应用占据 Web OS 中独立的全屏空间。
- 桌面空间组织不同的窗口集合，保留窗口原来的布局和所属关系。
- 浏览器全屏由浏览器控制，隐藏浏览器工具区，并受用户手势和安全退出规则约束。

应用进入全屏时需要记录返回的桌面和几何位置。退出后回到原处；在总览中切换桌面、从程序坞重新激活应用，也应找到它实际所在的空间。移动窗口时改变所属关系，避免卸载再重建项目 iframe。独立全屏空间的组织方式参考了 [Apple 的多空间指南](https://support.apple.com/guide/mac-help/work-in-multiple-spaces-mh14112/mac)，具体键盘能力仍按当前浏览器报告。

总览拖放则需要一个明确的提交边界：超过拖动阈值才进入拖放，只有落在有效普通桌面上才提交，取消手势或失去页面焦点时不迁移窗口。全屏空间不作为普通窗口的拖入目标。拖动结束后还要抑制紧随其后的点击，避免刚放下窗口又激活错误对象。

验收不只观察动画。需要检查切换前后的项目 iframe 是否仍为同一节点、输入焦点是否归属可见应用，以及未保存文本是否仍在。相同节点能证明页面未被重建，不能独自证明实时连接始终正常。

## 让文件操作真正可恢复

文件管理从编辑和下载扩展到重命名、移动、复制、多选、废纸篓、放回原处与撤销时，风险不再只在界面。服务端必须知道用户刚才选的是哪一个版本，以及中断发生在文件变动之前还是之后。

### 先核对修订，再处理冲突

列表返回文件修订标识。写入、移动、重命名、移入废纸篓或恢复时，客户端提交当前看到的修订，服务端再次核对实际文件。如果源已变化、目标已存在或路径关系不合法，停止并要求刷新，不能悄悄覆盖另一份内容。

所有操作都限定在授权应用数据根内。符号链接、目录连接、特殊文件和异常硬链接被拒绝；目录递归和复制总量具有明确上限。应用目录的权限并不等于整个集群文件系统的权限。

### 废纸篓保留内容和来源

“移入废纸篓”把内容移入受保护的存储区，并保存原位置和操作信息。放回原处重新核对内容、修订、来源和目标冲突。界面只显示经过投影的名称、时间和来源，不把内部物理位置暴露为任意文件入口。

本轮没有增加永久删除或自动清空废纸篓。容量不足时拒绝新操作，并明确说明，不通过静默丢弃旧内容来腾空间。可恢复的放回操作参考了 [Apple 的废纸篓说明](https://support.apple.com/en-ie/guide/mac-help/mchlp1093/mac)，但本项目的实际数据边界与宿主 Finder 不同。

### 中断后先认定事实，不重投命令

一次多文件操作按以下顺序进行：

1. 校验整组选项、修订、目的地、大小和容量限制。
2. 原子保存操作意图，再处理文件变动。
3. 每完成一步就记录已完成状态，最后提交汇总。
4. 进程重启后对照实际源、目标和内容指纹，分类已完成、未完成或不确定步骤。
5. 对已证明完成的部分提供撤销；不确定状态保留为中断，不再次执行原命令。

撤销也可能中断，因此它本身需要记录，而不是只在浏览器里保留一个回调。若目标已被后续编辑、原位置被占用或证据不完整，应停止恢复，避免为了“撤销成功”覆盖用户的新数据。操作记录有界，持久撤销不等同于无限历史、备份系统或跨机器事务。

## 通知与专注要接到真实事件

本轮通知中心投影既有任务和活动字段，按来源分组，支持展开、已读、单条清除、分组清除及清空视图。点击任务通知会定位到对应的真实任务，记录不存在时显示未找到，而不是打开一个看似相关的首页。

通知的清除与源数据分开：清除通知只保存该用户已处理的通知标识，不删除任务或审计记录。已读、隐藏及通知偏好按主人分区，有界保存；签出或切换身份时立即停止显示旧主人的内容。浏览器存储不包含通知正文或原站秘密。

公网验收还发现，原生项目的普通后台 HTTP 与 WebSocket 传输也有审计记录，直接投影会占满未读列表并暴露无助于操作的实现细节。本轮按已识别的准确事件类型、来源、方法和状态过滤这些常规传输记录，不做宽泛关键词屏蔽；授权启动、文件操作、失败与未知事件继续保留。修补发布后，展开的工作空间活动中已不再出现这些普通传输通知，原始审计没有修改。活动通知只进入工作空间总览，不把审计标识冒充节点定位；任务通知继续携带真实任务目标。

专注模式控制 Web OS 自身的新事件横幅。首次载入的历史记录不逐条弹出，开启专注后不自动展示新的事件横幅，通知中心仍可查阅；用户主动操作的成功或错误反馈继续显示。它没有修改宿主系统的勿扰模式，也不会禁止其他浏览器标签或其他设备发出通知。

分组、清除和专注入口的交互参考了 [Apple 的通知指南](https://support.apple.com/guide/mac-help/use-notification-center-mchl2fb1258f/mac)。本轮没有仿造系统级通知投递、跨设备 Focus 同步或智能摘要。

## Spotlight 的结果必须带着目标

搜索结果不仅是标题，还应带有类别与明确动作：

| 类别 | 确认后的动作 |
| --- | --- |
| 已有窗口与应用 | 激活对应应用，找回其窗口和所属桌面 |
| 文件 | 打开对应文件，而非只跳到应用数据根目录 |
| 节点与任务 | 定位真实记录，清除阻挡目标的筛选并短暂突出显示 |
| 系统设置 | 进入具体设置分类，避免要求用户再次查找 |
| 桌面操作 | 执行明确、已提供的工作空间动作 |

文件搜索使用受认证的服务端有限搜索。输入停顿后再请求，旧请求取消，旧查询的结果立即从新查询视图撤下。服务端限制查询长度、目录深度、访问条目与结果数，返回字段有固定投影；客户端设置请求超时并丢弃过期结果。达到结果限额时提示缩小范围，不在前端并发遍历整个磁盘；客户端取消不等于服务端已有完整的执行期限控制。

异步结果插入时，以稳定结果标识保留当前选择，避免用户按下确认键时目标突然变化。节点和任务深链接同样使用真实记录标识，只在收到一次新导航请求时滚动、聚焦和突出显示；后台刷新不反复抢焦点。

本轮借鉴的是统一查找和执行入口，参见 [Apple 的 Spotlight 指南](https://support.apple.com/guide/mac-help/search-with-spotlight-mchlp1008/mac)。全文索引、邮件消息、计算与单位换算、系统级快捷动作仍是独立差距，不能由一个搜索框外观代替。

## 用一条连续工作流验收

实现已通过分项模型、组件、接口与文件系统检查；普通 Linux 上的真实文件操作检查与 Windows 上的检查分别保留结果。发布后已取得以下有限公网证据：

| 流程 | 实际结果 |
| --- | --- |
| 版本与会话 | 服务运行态复核通过；公网重载后既有 SSO 自动回到桌面 |
| 全屏与桌面组织 | 应用进入全屏后铺满工作区，显示桌面再返回仍保留全屏；调度中心所列窗口均未最小化或隐藏，原有独立全屏空间仍保留 |
| 原生监控 | 默认在线列表的真实指标持续变化 |
| 测试文件 | 创建文本、重命名后选中与焦点保留、移入废纸篓、放回原处，再由搜索打开并读回文本；最后再次移入废纸篓保留内容 |
| 精确目标 | 节点搜索实际聚焦对应的真实节点；新建只读扫描完成后，点击通知准确定位该任务 |
| 通知去噪 | 修补后展开工作空间活动，没有普通后台传输通知；原始审计保持不变 |

后续分别在台前调度开启和关闭时，公网完成了设置应用全屏、显示桌面、从程序坞切到任务、从总览回到原设置全屏空间，再退出全屏的连续操作：桌面实际可操作，退出后设置成为前台且内容区获得焦点。关闭台前调度时，随后经程序坞在任务与设置之间切换也能正确交还焦点，验收后恢复原开关状态。

测试数量和这些局部操作都不能代替完整验收。下面的连续流程仍用于后续补齐，未在上述结果中列出的分支继续保留为待验收：

1. 打开文件与一个真实项目，切换、隐藏、最小化、关闭窗口，再区分退出应用。
2. 进入应用全屏、返回原桌面，在总览中迁移窗口，核对内容与页面节点连续性。
3. 创建测试目录并多选文件，重命名、复制、移动、移入废纸篓、放回和撤销，确认内容一致。
4. 刻意制造修订变化和同名冲突，确认操作停止；仅在隔离数据中模拟中断并验证重启后的恢复分类。
5. 产生真实任务事件，检查通知分组、已读、清除、专注和深链接，确认源任务及审计仍存在。
6. 用搜索进入文件、节点、任务及设置，快速改变查询，核对选择、取消请求和键盘焦点。
7. 重载工作空间，核对各项保存范围；退出、重新登录和长期连接另行验收。

发布时只替换受审的桌面后端和前端制品，身份、验证器绑定、钥匙串、业务地址与防火墙保持既有边界。文件事务存储需处在服务已获授权的可写数据范围内；先检查运行账户和沙盒，不为新增功能扩大到宿主根目录。

| 范围 | 本轮已实现并发布 | 仍需实现或验证 |
| --- | --- | --- |
| 应用与窗口 | 独立生命周期、最近使用切换、隐藏及退出语义 | 同一应用多独立文档窗口、更多原生应用菜单与完整键盘矩阵 |
| 桌面组织 | 应用全屏空间、普通桌面迁移、保留页面状态 | 多显示器、硬件手势、所有浏览器环境与辅助技术组合 |
| 文件 | 授权目录内的真实事务、废纸篓、修订检查和有界持久撤销 | 任意远端卷、系统文件管理、永久删除、无限撤销与备份恢复 |
| 通知与专注 | 真实任务及活动投影、分组、已读、隐藏和工作空间专注 | 系统推送、跨设备同步、全应用通知与智能处理 |
| 搜索与设置 | 分类动作、有限文件搜索、真实记录与设置深链接 | 全文索引、宿主全盘搜索、计算换算和广泛自动化 |

项目仍以完整工作空间为目标。下一步应沿连续操作补齐行为、数据和恢复边界，再核对材质与动效；新增功能要能解释它操作了什么、保存在哪里、失败后怎样继续。完整需求继续维护在[路线图](../ROADMAP.md)，此前窗口组与实时监控实践见[相关章节](14-stage-manager-and-native-metrics.md)。
