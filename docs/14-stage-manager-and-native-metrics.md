# 可恢复的窗口、台前调度与原生监控

**状态：已发布，并取得真实公网交互与监控读取证据。** 平铺窗口可拖回浮动；文件与 Beszel 合组、切换另一应用组再整组返回后，搜索内容保留，五个原生项目 iframe 仍为原来的节点。Beszel 无需再次输入原站密码，已显示既有系统的 CPU、内存、磁盘、温度和 CPU 历史曲线；后续升级后既有 SSO 自动回桌面，监控读数再次显示。实时 SSE 仍在观察，本轮尚未实测新监控连接在锁定时关闭。这些结果不代表全部管理业务或全部 macOS 功能通过。

上一阶段解决了[远程管理页面进入 OS 会话边界](13-mesh-native-sessions-and-release.md)的问题。这一阶段同时处理两个影响日常使用的缺口：窗口平铺后应该能自然拖回，应用分组切换时也应保留原页面与连接；监控应用则应通过经过核验的原生身份接入，而不只是显示一个打开原站的图标。

## 吸附后拖不回，根因在窗口状态

旧实现把平铺或展开状态视为禁止拖动。窗口贴到屏幕边缘后，标题栏因此失去拖动能力。只调整圆角、透明度或动画曲线，无法解决这个状态问题。

修复把窗口的浮动几何与当前平铺布局分别保存。按下标题栏时，记录窗口、指针位置和当前显示边界；移动超过阈值后，再恢复浮动尺寸并开始拖动。轻点标题栏不会误触发还原。

恢复时需要保留指针锚点。水平方向依据按下位置在标题栏中的比例计算新位置，垂直方向保留标题栏中的抓取偏移。这样，从窗口中部或右侧抓起时，恢复后的标题栏仍接在指针下方，而不会突然跳到另一边。恢复后的几何还要限制在可用桌面区域内，避免标题栏跑到无法操作的位置。

另一个容易遗漏的细节是同次拖动的重新吸附：窗口刚脱离平铺时，指针可能仍在原来的边缘区域。如果立刻再次计算吸附，松手又会回到原布局。实现要求指针先离开边缘区域，再允许本次拖动触发新的吸附。取消操作则恢复拖动前的布局；绿色窗口按钮也将平铺识别为可以还原的状态。

窗口平铺的操作参考了 Apple 的[窗口平铺指南](https://support.apple.com/guide/mac-help/tile-app-windows-mchlef287e5d/mac)。指针捕获、状态保存、移动阈值和取消处理，则是本项目根据网页窗口模型完成的实现。

拖到边缘自动平铺另设持久化偏好，按主人的操作习惯默认关闭。用户仍可从绿色窗口按钮选择布局；关闭边缘平铺也不会禁用台前调度的拖入合组和拖回拆组。

## 台前调度需要真实的组与连续的页面

Apple 的[台前调度指南](https://support.apple.com/guide/mac-help/use-stage-manager-mchl534ba392/mac)将近期应用放在左侧，允许把应用拖入中央组成工作组，并在切换时恢复整组。指南还说明了从组中移出窗口、隐藏近期应用后从左缘唤出，以及开关台前调度的使用方式。

实现据此建立独立的应用组状态，记录每组的成员、所属桌面和当前前台组。把左侧预览拖进中央可以合组，把组内窗口拖回左侧可以拆组；点击另一组时恢复其成员，而不是只激活其中一个窗口。关闭窗口后会清理组关系，避免留下空组或让同一窗口重复归属。

应用组、最小化和 Spaces 各自保留明确含义：

| 状态 | 对窗口的影响 |
| --- | --- |
| 后台应用组 | 原窗口保持打开，切换整组可恢复 |
| 最小化 | 用户主动收起窗口，通过相应入口恢复 |
| 其他 Space | 窗口属于另一个虚拟桌面 |

近期预览使用已挂载窗口的浏览器绘制结果。切换布局只改变位置、缩放、可见性和输入状态，不创建第二份 iframe，也不因进入后台组而卸载原页面。这能避免切一次组就重新登录、丢失表单或重建实时连接。保持同一 DOM 节点只是连续性的基础，长期连接是否稳定仍须单独验收。

后台窗口和缩略预览设为不可交互，避免点击穿透或键盘输入误送到隐藏页面；输入桥同时接收活动窗口状态。隐藏侧栏后，其中的控制按钮也退出键盘焦点顺序。键盘循环仍可找到当前 Space 中的后台组，选中后显式恢复整组并聚焦真实窗口。

台前调度提供开关，关闭后恢复普通多窗口布局；近期应用栏也可单独隐藏，并通过左缘唤出。点击壁纸显示桌面、从 Dock 恢复应用，以及合组和拆组都应更新同一份状态。动效围绕这些状态变化展开，并响应减少动画偏好。

本地已核对拖离平铺、合组与拆组、显示桌面、Dock 恢复、左缘唤出和键盘跨组切换。发布后，真实公网的既有平铺窗口也已用标题栏拖回浮动状态；台前调度可从控制中心开启。真实文件窗口与 Beszel 已实际合组，切到 Harness 后整组返回，文件搜索内容保留，随后已清除测试搜索；五个原生项目 iframe 的节点身份前后相同。这次观察证明了页面与输入状态的连续性，不能代替实时连接的长期稳定或撤销验收。

## Beszel 可信头必须先有来源隔离

本次适配面向经过核对的 Beszel 安装版本。该版本支持可信身份请求头，但没有较新版本中的受信代理地址限制。其[官方中间件实现](https://github.com/henrygd/beszel/blob/v0.18.7/internal/hub/api.go)会根据该头查找用户，因此不能在原来的通配监听上直接启用。

实现采用先隔离来源、再启用可信身份的顺序：

1. 将 Hub 收窄到 loopback，保留专用服务身份。
2. 为原有的精确 Tailnet 入口提供净化代理，剥除可信身份头及相关外部身份声明；保留原生密码登录和原生认证请求。
3. 仅让受工作区密码加 Authenticator 保护的 OS 代理，在服务端注入已经核验的身份映射。
4. 检查真实监听集合与原入口健康，并用带重复、大小写变化身份头的请求验证旧入口仍然拒绝身份冒用。

正反对照使用一个明确要求原生认证的只读接口。不能随意选择列表接口来判断授权是否失败：[PocketBase 的 API 规则说明](https://pocketbase.io/docs/api-rules-and-filters/)明确指出，列表规则不满足时可能返回空列表和成功状态。首页或列表的单个成功响应都不能证明已经登录，更不能证明管理业务可用。

原生嵌入策略由 Beszel 自己设置。该版本的[页面处理代码](https://github.com/henrygd/beszel/blob/v0.18.7/internal/hub/server_production.go)支持应用侧 CSP；实现只允许精确桌面父来源，并同时允许经过核对的原生初始化脚本与固定桌面引导脚本。代理不通过全面删除安全响应头来制造“可以嵌入”的表象。

拥有主机 root 权限或被授权的主机 SSH 访问者，仍在主机信任边界内。收窄到 loopback，解决的是网络入口伪造身份的问题，不能将同一主机上的高权限调用方变成不可信客户端后仍承诺完全隔离。

## 原生 JWT 留在服务端，实时订阅也受租约约束

管理员身份映射来自本人已经确认的既有管理员。私密导入只读取身份所需字段，保留原密码、MFA 和角色；不读取密码或数据库签名种子，也不自行伪造原生 JWT。

工作区解锁后，服务端以固定来源上的受信身份完成原生认证。真正的 PocketBase JWT 留在后端，浏览器获得与当前工作区租约绑定的不透明句柄。句柄保留原前端需要的结构，但不具备直接登录原站的能力；代理先验证句柄与租约，再在服务端恢复原生授权。

SSE 是持续连接，需要同样处理。原生客户端标识被映射为租约内的不透明值，订阅请求只能使用同一租约的映射。对于自定义实时指标通道，每个系统都先向原站验证当前身份的读取权限，不能因为用户已登录就信任浏览器提交的任意系统引用。

事件逐项经过结构和敏感字段检查，再交给网页。实现限制单事件大小、待处理字节、每租约连接数量和空闲时限，并按下游需求读取，避免后台无限积压。消费者取消、网络中断、锁定、租约到期或代理关闭时，都要取消原站读取并清理客户端映射。只拒绝后续请求，不能证明既有 SSE 已经停止。

当前接入面向系统列表、指标读取和实时订阅。系统列表、指标和历史曲线已取得实机证据；SSE 完成了一次约三分钟的同连接实机观察，后续定期事件继续到达，不能据此承诺永久稳定。未经审查的管理写入、凭据生成、配置导出及 Agent 连接保持受限。保留原站管理员身份，并不意味着浏览器获得所有原生敏感能力。

## 实机暴露的两层认证冲突

第一次实机验收中，桌面已经解锁，原生应用也完成了首次认证，但带临时授权头的后续接口返回纯文本 401，并附带 Basic 登录挑战。没有该头的首次认证请求却能成功。与此同时，直接在受信本机路径读取原站，能够取得已有系统与 CPU 字段。这个对照说明不能把空列表直接归因于监控没有数据。

问题出在前置认证与应用认证共享了 `Authorization`。Authelia 的[代理授权说明](https://www.authelia.com/reference/guides/proxy-authorization/)规定，默认策略先尝试该头，再尝试会话 Cookie；头存在但认证失败会立即短路。原生应用的临时句柄并非 Authelia Basic 凭据，因此请求在抵达 OS 代理前已经被拒绝。

修复范围限定在监控应用的认证子请求：向前置身份服务提交会话 Cookie 和既有可信请求元数据，同时移除该子请求中的应用授权头。原始业务请求仍保留临时句柄，由 OS 代理检查租约和已签发句柄，再恢复服务端原生授权。Caddy 的[forward_auth 文档](https://caddyserver.com/docs/caddyfile/directives/forward_auth)说明它代理请求的副本，因此可以分别处理这两个请求。匿名用户仍须进入工作区的双因素认证，不能通过去掉整层认证来“修复登录”。

另一个独立问题是认证能力接口的结构检查：其中 `password` 是描述登录能力的对象，不是密码内容。适配器对此单一接口使用与已核对原站版本一致的严格投影；普通业务记录继续拒绝敏感字段。OAuth 流程中的 state、授权 URL 和 PKCE 材料也不返回网页。两项修复分别验证，不能用其中一项的单元测试代替公网业务结果。

## HTTP 空闲计时与原生实时订阅

实机还暴露了一层容易被单元测试漏掉的问题：订阅握手成功、能够收到第一条事件，随后在正常的无消息间隔中断开。原站按分钟更新资源，代理运行时的 HTTP 空闲计时却更短，浏览器因此反复报告连接中断。仅凭握手成功不能标记实时业务通过。

修复在已经授权的精确原生 SSE GET 分支中，使用 Bun 的[请求级 timeout 接口](https://bun.sh/docs/api/http)关闭该请求的通用 HTTP 空闲计时；普通请求不受影响。适配器自己的租约截止、流空闲、撤销、取消和背压限制继续生效。合成测试使用真实运行时跨过实际计时器触发边界，再等待后续事件，避免只等很短时间就误判通过。

发布后，真实公网浏览器通过同一个 SSE GET 连续约三分钟收到系统事件，跨过了之前反复失败的短周期。长期稳定、断网恢复和实际锁定仍须分别记录，不能由这一段观察推导出来。

## Tailnet 清单与资源采样分开验收

全设备接入先读取设备名称、操作系统和内网地址，保留原有监控记录，只创建明确缺失的原生系统。登记本身不写 CPU、内存或磁盘数据。原生页面对尚未采集的设备可能显示灰色零值，这些是占位，不能解释为真实零负载。

随后按平台部署固定版本官方代理：Linux 主机使用独立非 root 服务和精确 Tailnet 监听；Windows 可使用当前用户代理、持久数据目录和加密连接身份；无持久用户会话的主机另评估容器服务。进程运行、采集端口可达、原生数值与历史记录分别验收。虚拟网络身份还要确认宿主或容器归属，避免把同一宿主资源重复计入多台设备。

代理连接只使用必要的 Hub 公钥或该设备专用的原生令牌。令牌在进程内生成，经受限文件与 SSH 私密传输，按平台加密保存，不进入聊天、命令参数或公开仓库；已有应用管理员身份不因此交给网页。离线、管理通道缺失或官方未支持的平台继续标明未采集，不用假数据补齐。

## 回退必须包括完整加密钥匙串

新应用接入会改变代码、路由、身份映射和源站监听。只把版本指针切回去，可能留下旧代码无法识别的新钥匙串记录。

发布事务因此先停止后端，保存完整旧加密库及其权限元数据，再保存相关配置基线。身份导入只允许增加目标记录，既有记录的密文保持原样。发生失败时，必须先恢复完整旧加密库和元数据，再启动旧版本解析器；不能只删除看起来新增的字段，也不能重新生成旧凭据来拼出一个“近似恢复”的库。

源站隔离、双入口网关与精确 DNS 各自检查和记录阶段。回退只能处理本事务确定拥有的改动；遇到其他管理员的并发编辑或无法确认的快照，应停止相关后端并保留待查状态，避免覆盖新配置或启动不兼容的旧代码。已公开后的故障也须依据实际阶段处理，不能无条件恢复旧库。

这次接入之后，认证子请求修复只更新受影响的网关路由；桌面后端和身份服务当时没有重启。独立的认证能力元数据修复则随后端与静态资源升级发布，不重新导入钥匙串。既有 SSO 自动返回桌面，原生监控再次显示真实读数。这两个阶段保留不同的变更范围和证据。

## 传输、清单与固定输出也需要实证

一次传输已取得正确归档摘要，却因工具落盘权限比预期宽而在解包前被拒绝。兼容范围只限新建私有暂存目录内、已验证所有者的普通单链接归档；在同一文件描述符上收窄权限后，重新核对稳定签名与摘要，再进行拒绝链接和路径穿越的解包。秘密文件及其他来源读取规则没有一起放宽。

另一次本地打包误把 manifest 自身列入有效载荷清单，发布器在安装或切换现网之前拒绝。修正时保留原归档、收据和私有备份，只改明确识别的暂存输入，沿用同一份已构建源码；不能通过更换来源说明来掩盖打包错误。清单应描述有效载荷，清单自身的摘要由外层受审入口固定，避免自引用。

固定输出也有端到端协议：内部脚本、外层包装器和自动调用工具的白名单必须逐项兼容。只检查新增字段会遗漏原有成功行中的数字。后续回归把实际成功、失败与回退输出送过完整过滤链；合成测试、传输检查、发布回执与真实浏览器业务仍分别记证据。
