# 从设备清单走到真实采集

**状态：多台 Linux 和 Windows 设备已完成实际采集，公网桌面的原生监控窗口持续收到 CPU、内存、磁盘和运行时间。** Windows 后台服务的安装、恢复配置与独立状态读回已通过。部分设备还提供温度或电池信息。整机重启恢复、所有传感器以及全部设备的接入仍需分别验收；登记成功不能替代采集成功。

本文保留实现顺序与踩坑经验，移除设备标识、网络地址、个人路径、真实回执和凭据。完整受限运维源码与生产输入分别保存在私有环境；本仓库仍是教程，不包含可直接运行的完整发行包。

## 把“看见设备”拆成可以验证的阶段

| 阶段 | 能证明什么 | 还不能证明什么 |
| --- | --- | --- |
| Tailnet 清单 | 设备已登记，具有网络身份；在线是某一时刻状态 | 有管理员通道、安装了采集器 |
| 原管理通道认证 | 已授权的账号可以连接经过主机密钥核对的入口 | 该入口就是目标宿主；容器也可能接受登录 |
| 主机与部署关系核验 | 可以区分宿主、虚拟机、工作容器和网关 | 采集器已经运行 |
| 服务运行与配置读回 | 精确程序、目录、服务账号和启动策略符合预期 | Hub 能连通、原生界面已有新数据 |
| 原生新采样 | 指标来自真实采集，能够观察后续更新 | 已经历重启、断连、恢复和所有传感器测试 |

资产可以预先出现在 Beszel 中，离线或未安装的记录应保留清楚的状态。灰色零值不是采样证据。完成时同时检查原生客户端版本、连接方式、资源读数和后续更新；必要时把磁盘、CPU 型号或内存容量与源主机比对。

## Linux：让采集器成为独立的后台服务

在可管理的 Linux 主机上，使用经过核验的官方固定版本，新增独立非 root 账号、配置和数据目录，以专用服务运行。监听只绑定已经确认的内部地址。先从 Hub 测试端口，再观察原生采样，不先假设失败来自防火墙。[Beszel 官方安装指南](https://www.beszel.dev/guide/agent-installation)介绍了二进制与容器等安装方式；本项目实际验证的是固定版本，不能直接套用文档中未来更新的全部参数。

受限主机也可以使用已有、获授权的容器管理通道。需要具体说明容器能看到哪些宿主资源。本项目用同一文件系统上的专用空目录作只读 bind，核对其 statfs 后采集主盘容量；没有因得到磁盘读数，就把 Docker 管理、SMART 或所有传感器都标为完成。

## Windows：路径看起来相同，外部任务未必能访问

第一条 Windows 路线使用当前用户的受限计划任务。安装期间遇到一个问题：打包宿主内可见的本地资料目录，和外部计划任务实际可见的位置不同。应比较打开句柄得到的物理路径，并让外部调度器执行无状态探针，不能只在原进程中检查文件存在。

本项目随后选择已验证的物理用户目录，保留原加密身份文件的字节、旧任务定义和回退材料；以固定系统目录作为任务工作目录。工具调用结束后，独立确认任务仍运行、精确采集进程只有一个，并在原生界面看到新采样。该用户级路线在注销后停止，不能泛化为登录前系统服务。[Microsoft 的 MSIX 虚拟化说明](https://learn.microsoft.com/en-us/windows/msix/desktop/flexible-virtualization)解释了受配置影响的重定向机制；这里的具体路径差异来自现场验证，不代表所有打包应用都有相同行为。

另一台 Windows 采用专用系统服务。已有授权管理凭据由 Windows 身份机制消费，助手不导出密码或凭据正文。远程连接经过已知内部管理通道，安装过程只处理一个固定服务及其目录，不开启通用远程命令入口。

服务包装程序需要真正响应 Windows Service 生命周期，启动和停止自己的采集子进程。上传时先原子建立受保护的目录和文件 ACL，再写入已核验程序；启动前复核机器、实际账号、物理路径和程序摘要。延迟自启、既有网络服务依赖、有限重启退避和失败处理均只作用于本服务，并逐项读回。官方 Windows 安装路线使用服务管理工具；本项目另实现了一个用途固定、经过审查的服务包装程序，而不是把普通程序路径直接冒充服务入口。

## “创建阶段失败”不一定表示没有创建

本次 Windows 部署中，服务已经创建，但紧随其后的配置读回被客户端的严格解析器拒绝，后续启动没有发生。原始阶段标签不足以判断远端状态，直接重跑可能进入未知的半完成状态。

恢复顺序如下：

1. 只读查询精确服务、受保护文件及原上传回执，确认是否真的创建、是否启动过。
2. 对照现场返回的结构与有效长度修正解析。已观察到的依赖字符串表示和补零缓冲，只作精确兼容，不通过任意 trim 或忽略尾部放宽判断。
3. 仅在原程序完整、服务从未启动、恢复策略仍为默认、没有其他生命周期标记时续接。
4. 首次写入前重复前提检查；沿用这一个服务完成配置、启动和读回，不再上传或创建。
5. 端口已能从 Hub 到达，因此没有新增防火墙规则。最终由公网原生指标与独立状态查询共同验收。

恢复工具与普通安装工具应保留各自有限入口。结果未知时先查现场；不要用“幂等”作为采纳未知目录、未知服务或已有同名规则的理由。回退只处理具有确切归属证明的自有服务，保留数据和审查材料。

## 网络网关也需要明确指标属于谁

同一宿主可以运行独立的用户态 Tailscale 实例，在 Tailnet 中表现为不同的逻辑节点。本项目已通过实际进程、专用 socket 返回的 Self，以及运行命名空间核实这种共享关系。SSH 登录进入的工作容器、后端项目虚拟机和承载网络实例的宿主，需要分别确认归属。

当前使用的 Beszel 原生界面没有资产别名功能。确认共享宿主后，本项目保留逻辑资产的原地址和访问权限，在名称中明确共享关系，并暂停重复主机采样；真实资源指标只保留宿主现有的采集源。这样既保留网络资产记录，也能明确指标属于哪台宿主。

这次变更仅涉及名称和状态。写前保存变更意图，写后用 GET 读回；响应不确定时先用 GET 核对现场状态，再决定如何恢复事务，确认前不重复发送 PATCH。

最终验收核对采集源的最新样本时间和真实资源读数，确认数据仍在合理的新鲜度范围内。设备在线只证明当时的连接状态，不能代替持续采样的证据。

## 将本次流程留成可复用工具

正式私有源码只保留采集服务、有限安装与恢复入口、状态检查、固定传输和测试。调查脚本、真实回执、运行依赖、编译制品、公开密钥输入以及任何账号材料分别管理，不混入源码导出。

状态查询使用与部署相同的精确程序和配置合同，查询不会顺便修复、重启或重置身份。纯测试验证权限与生命周期边界，实机检查验证安装结果，公网原生采样验证实际用途；三类结果分别记录。后续重启与恢复演练仍需单独留下证据。
