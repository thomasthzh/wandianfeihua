# 万点飞花实施教程：从桌面项目到双入口验收

这份教程帮助你准备一套单用户集群 Web OS：从网页桌面启动已有项目，用密码和 Authenticator 登录，并分别通过 IPv4 边缘入口与 IPv6 核心入口访问。

**仓库提供手册与示例，不提供可运行的桌面源码、服务器二进制或完整部署包。** 以下步骤包含你需要准备的组件、接口契约、检查方法和验收顺序。不要在克隆后直接尝试 `bun start`，也不要把示例配置当作某个未提供程序的真实配置格式。

所有地址都是文档值，角色为 `core-v6` 与 `edge-v4`。具体布局先看[架构说明](01-architecture.md)，可从[拓扑清单](../examples/topology.env.example)整理自己的环境。不要把填好真实信息的副本提交到 Git。

本项目的核心、边缘及业务 DNS 已启用并通过自动检查。本人已在公网完成密码加 TOTP 正向登录、主动锁定重登、窗口总览与并排、实际节点状态、授权文件创建编辑和刷新回读、真实扫描及刷新后任务保留。四个受保护候选加载了预期原站页面，业务仍待验收。首轮发布曾因 BFF 的 `INVALID_NODE_ENV` 停止；本人恢复时环境规范且未修改，四阶段重校验通过后才激活。下文仍是完整的实施与验收要求，不能把已经通过的部分扩大为负向认证、SMTP、完整注销、独立外部 IPv6 或全部应用业务均已通过。

## 0. 先定义这次要交付什么

第一轮建议只接入一个允许嵌入的只读项目，用它走通完整链路，再逐个增加应用。单用户版本至少应有这些可验证行为：

1. 未登录时只能进入登录流程，不能通过 API、静态入口或应用地址绕过认证。
2. 密码正确但没有 TOTP 时仍无法进入受保护桌面。
3. 登录后出现登记过的应用；点击图标打开窗口，最小化后能从 Dock 恢复。
4. 应用实际加载自己的页面、资源和所需连接，保留自身认证。
5. 会话过期和注销可预测；受保护 API 不继续返回数据。
6. IPv4 与 IPv6 分别测试成功；一条路线成功不能替另一条签字。

把“界面完成”“只读传输通过”“管理功能通过”“公网验收通过”分别记录。未经实现的功能显示为禁用或演示，不能伪造在线数据。

## 1. 准备桌面、BFF 与发布产物

你可以自行实现这些组件，也可以选择已有且许可兼容的项目，但需要能掌握认证和代理边界。

| 组件 | 需要准备的内容 | 第一轮通过条件 |
| --- | --- | --- |
| 桌面前端 | 桌面图标、搜索、菜单栏、Dock、窗口管理、登录状态、移动适配 | 刷新、窗口切换、缩放和键盘操作正常 |
| BFF | OIDC 回调、服务端会话、owner 白名单、CSRF、登记表与受控 API | 未认证请求被拒绝，浏览器无身份 token |
| 应用连接器 | 固定目标、探测、HTML 与资源转发、必要的 WebSocket | 不接收任意 URL，不绕过原应用权限 |
| 静态前端产物 | 已构建的静态文件与安全响应头策略 | 不包含真实 secret 或开发环境后门 |
| 服务定义 | 独立服务账号、可写状态目录、权限和日志策略 | 服务以预期非特权身份运行 |
| 发布包 | 版本清单、依赖版本、制品摘要、配置示例与回退说明 | 可核验制品，身份与秘密不打包 |

桌面视觉可采用 macOS 风格的菜单栏、Dock、交通灯窗口按钮和适度透明外壳；不要依赖照搬一整套模拟器的认证代码。窗口的关闭、最小化、最大化按钮应有可访问名称，内容区域要能滚动，最小化窗口不应继续遮挡桌面点击。小屏幕优先保证当前应用可用。

建议先定义窄接口，再做界面。下面是接口职责示意，路径由你的实现确定：

| 接口职责 | 应返回或执行的内容 | 必须拒绝的请求 |
| --- | --- | --- |
| 获取会话 | 是否登录、有限展示信息、登录入口 | 身份 token、TOTP 密钥或完整上游凭据 |
| 获取应用 | 只返回允许当前 owner 使用的登记项 | 浏览器临时指定的代理目标 |
| 启动应用 | 校验登记状态后返回受控入口 | 未登记来源、任意重定向 |
| 获取节点摘要 | 固定字段、时间与数据来源 | 任意文件读取、任意 shell |
| 创建任务 | 仅接受明确允许的任务类型和参数 | 未授权命令、无限超时或无限并发 |

本地视觉演示与生产认证要使用明确的不同模式。生产模式缺少 issuer、owner 或 secret 时应退出，不应退回演示登录或测试会话。

## 2. 按部署证据清点真实项目

从你管理的服务单元、容器编排、反向代理配置和部署记录开始。不要靠端口扫描或猜 URL 发现项目，也不要为“自动接入”读取历史密码库和环境秘密。

给每个项目填写一条记录：

| 项目 | 示例填写要求 |
| --- | --- |
| 显示名称和稳定标识 | 例如“监控台”；标识不随地址变动 |
| 节点角色 | `core-v6` 或另行登记的节点角色 |
| 规范来源 | 从实际配置确认；不要把隧道连接地址当来源 |
| 传输目标 | Tailnet 或受限内部通道，和规范来源分开 |
| 首页、探测与资源路径 | 从实际首页或部署配置获得，不猜路径 |
| 协议 | HTTP、HTTPS、WebSocket 以及必要的子协议 |
| 原生认证 | 是否必须再次登录、是否有只读账号 |
| 嵌入支持 | 官方设置、CSP、Cookie 和跨来源限制 |
| 操作权限 | 第一轮只读；管理能力按操作逐项批准 |
| 当前状态 | 待核实、受限、只读已验证、交互已验收 |

只读连接验证至少包括：预期应用的 HTML、一条 HTML 中实际引用的静态资源、必要的重定向，以及项目确实需要的协议连接。WebSocket 可以先验证握手或协议初始消息，不发送管理命令。HTTP 200、端口可连接和正确应用页面是三个不同的证据。

如果用隧道，明确区分“连接到哪里”与“上游期望谁来访问”。Host、Origin、Cookie 和重定向策略要按上游真实要求处理，不能通过关闭来源校验解决报错。

## 3. 建立单 owner 的双因素身份

示例身份入口为 `https://auth.os.example.net`，桌面为 `https://os.example.net`。本项目的身份配置验证基线是 Authelia **4.39.28**；选择其他版本时重新对照官方配置与 CLI，不能假设参数一直兼容。

### 身份服务的准备顺序

1. 创建独立服务账号、私有状态目录、用户数据和秘密文件；不要与应用发布包混放。
2. 为 owner 生成强密码的安全哈希。不要把明文密码放在命令参数、环境展示、Git 或教程截图里。
3. 设置受保护入口的密码加 TOTP 策略。首次登记验证器时，二维码和恢复材料只在本人受控流程中处理。
4. 配置真实 SMTP，测试发件、收件和恢复路径。示例邮箱为 `operator@example.net`，它不能实际收信。
5. 核对时间同步。保存经过演练的恢复方法，并把身份数据库与相关加密材料一起纳入受控备份。

如果已有可用的 TOTP 绑定，先确认原系统导出格式、目标版本导入格式和哈希兼容性，再决定是否迁移。整个过程由本人执行，不能把共享密钥发给助手或写进公开仓库。无法可靠迁移时，使用清晰不同的 issuer 名称并重新登记，避免手机中的旧条目被同名覆盖。

文件通知器可以用于受控测试；它不是 SMTP 投递已完成的证据。公网启用前应确认通知、恢复和错误提示的实际行为。

### OIDC 客户端与 BFF

注册一个专属于桌面的机密客户端，固定回调地址，例如 `https://os.example.net/auth/callback`。回调路径必须与自己的 BFF 实现完全一致；示例路径本身不会创建接口。

BFF 使用成熟 OIDC 库，服务端保存 client secret，执行 Authorization Code Flow、PKCE S256、state 与 nonce 校验。发现只允许固定可信 HTTPS issuer，并校验签名、issuer、audience 与有效期。身份服务对该客户端强制双因素，BFF 按已验证的协议核对该版本返回的认证方法声明；不能把浏览器提交的“已完成 MFA”标志作为证明。

用稳定 subject 确认唯一 owner，不能只比较邮箱或显示名。浏览器不持有 access token、refresh token 或 client secret，只持有 Secure、HttpOnly、host-only 的 opaque 平台会话 Cookie。配置绝对会话期限、一次性短时回调状态，以及写 API 的 Origin 与 CSRF 检查。

网关认证与 BFF owner 授权都要保留。身份服务自己的登录页面应按其集成方式独立路由，避免给登录页再套一层相同登录检查而形成循环。

## 4. 分离网络入口与现有服务

示例拓扑：

| 用途 | 地址 |
| --- | --- |
| IPv4 公网入口 | `192.0.2.10`，角色 `edge-v4` |
| IPv4 边缘局域网地址 | `192.0.2.20` |
| 核心 Tailnet 地址 | `100.64.0.10`，角色 `core-v6` |
| 边缘 Tailnet 地址 | `100.64.0.20`，角色 `edge-v4` |
| 核心公网 IPv6 | `2001:db8:120::10` |

核心网关分别接受公网 IPv6 和受限 Tailnet 转发。内部入口只信任明确的边缘来源，并固定可以转发的 Host 与路由；其他 Tailnet 节点不应自动获得代理入口权限。BFF 和身份服务只监听它们确实需要的内部接口。

先清点现有端口、监听、服务单元和网关站点，再选择独立端口或配置包含文件。不要用宽泛的新监听接管旧站点。以下命令是 Linux 上的只读清点示意，输出请留在自己的终端，不要原样上传：

```sh
ip -6 -o addr show scope global
ss -ltn
```

IPv6 需要检查有效期、地址稳定性和实际入口路由。有多个 global 地址时，先确定地址选择规则并人工复核；不能静默取第一条，也不能把旧记录直接填入绑定配置。

## 5. TLS：先演练，再签发，再分发

本仓库不包含可直接执行的签发脚本。使用自己审查过的 ACME 客户端和固定版本插件，在专属目录完成以下过程：

1. 准备 DNS 区域受限的 API token，权限仅覆盖需要的验证记录和必要的区域查询。由本人在隐藏输入终端提供，写入新建私有凭据文件；不要出现在 argv、普通日志或 shell 历史中。
2. 使用独立 config、work、log、账号和凭据路径。隔离系统默认配置、旧 renewal hooks、Cloudflare SDK 的 HOME/当前目录配置及继承环境变量。
3. 展示所选 CA 当时有效的条款链接，并取得本人明确接受，再启用客户端的同意参数。
4. 用 staging CA 做 DNS-01 演练。它仍会写入真实验证 TXT，但不会得到浏览器信任的生产证书。
5. 演练失败时保留专属目录。读取并分类失败，尊重 Retry-After；不要反复初始化、盲删账号或循环重试。
6. staging 成功后，再经本人明确确认向固定生产 CA 签发。证书策略应覆盖桌面主机名和计划使用的直接子域；如采用通配 SAN，明确其仅覆盖一个标签层级，不能替代根主机名本身。
7. 验证预期 SAN 集合、当前有效期、可信完整链和证书私钥匹配，成功后才记录生产签发结果。

不要把令牌权限扩大到整个账号来解决临时错误。证书签发成功也不等于已安装、可续期或公网可访问。

### 两个入口都要安装正确证书

两端终止 TLS 时，两端均需安装完整链与匹配私钥。文件应由 root 拥有，仅授予网关服务组必要读取权限，目录不允许其他用户写入。覆盖前确认旧文件来自已知安装；遇到未知文件先停止，不能自动覆盖。

私钥跨节点分发可使用一次性接收者公证书固定身份的 CMS 封包：AES-256-GCM 加密，RSA-OAEP/SHA-256 包装密钥。接收者私钥留在接收端；发送端固定核对接收者公证书摘要和有效期，封包只包含明确的证书数据字段，不接受任意目标路径。密文摘要经可信通道核对。

解密返回成功前，不得使用任何 stdout 内容，因为认证失败的解密工具也可能输出未验证明文。导入端再次校验证书链、SAN、有效期和密钥匹配。不要通过 Git、聊天或普通附件发送明文私钥。

更新两份普通文件时，应有失败回退和目录持久化步骤；它不等于整对文件在断电时原子切换。安装与服务重载分开验收。

## 6. 在不激活服务的情况下检查配置

检查用目标机器最终将运行的二进制和完整配置，不能拿另一台机器的新版本通过结果代替本机旧版本。本次核心专用网关验证使用 Caddy **2.11.7**，边缘保留既有 Caddy **2.11.4**；没有把边缘网关一并升级。两者均是本次验证基线，不代表后续无需升级评估。

| 检查阶段 | 必查内容 | 不能顺带做的事 |
| --- | --- | --- |
| BFF | 固定模式、issuer、owner、secret 元数据、静态产物、会话配置 | 启动监听或自动退回演示模式 |
| 证书 | 预期 SAN、有效期、完整可信链、私钥匹配、文件权限 | 重新签发、覆盖未知旧文件 |
| 身份服务 | 实际版本的配置验证、所需权限、OIDC 策略、通知配置 | 打印用户库或展开的 secret |
| 网关 | 实际版本的完整 adapt/validate、监听、路由、信任代理 | 重载旧网关、占用生产监听 |

配置检查应输出固定阶段与安全错误分类。不要为了便于求助，直接转发原始环境、用户数据、完整配置或未经审查的日志。失败时只定位失败阶段，在本人终端查看受控诊断。

如果升级专用二进制，确认对应单元明确处于 loaded 且 inactive 或 failed；`is-active` 的非零退出码本身不足以排除 activating 或 deactivating。保留已知旧版本与回退路径，不修改其他产品共用的二进制。

四阶段全通过后，先记录对应候选的“配置验证通过”，再单独记录入口激活结果。旧通过不能沿用到新候选。本次首轮 BFF 拒绝后安全停止；本人恢复重校验全部通过，随后核心、边缘和 DNS 激活及自动检查通过，尚不代表完整业务已验收。

遇到这类失败，先用有限分类区分规范值、缺失、已知格式或未知情况，不输出真实环境值。只对已审查的已知输入问题精确修复，保留备份与权限，再重新校验全部阶段。此次恢复没有修改已规范的值；合成引号复现不能当作现场根因，详见 [NODE_ENV 排错记录](05-troubleshooting.md#bff-曾拒绝-node_env恢复时未修改现场变量)。

## 7. 规划 DNS，再按依赖启动

先生成并审查 DNS 变更计划，查询现有 A、AAAA 和 CNAME，确认没有冲突。以下是文档中的目标值：

| 名称 | 类型 | 示例目标 |
| --- | --- | --- |
| `os.example.net` | A | `192.0.2.10` |
| `auth.os.example.net` | A | `192.0.2.10` |
| `os.example.net` | AAAA | `2001:db8:120::10` |
| `auth.os.example.net` | AAAA | `2001:db8:120::10` |

执行前重新核对现场 IPv6 和计划差异。DNS 查询与写入必须是两个明确步骤；计划工具不应隐藏写入。使用 DNS 代理服务时，也要验证它是否改变预期的直连 IPv4/IPv6 路径。

接下来按下列依赖组织激活。具体 service 名称取决于你自己的实现，本文不提供可直接执行的启动脚本：

1. 备份可回退状态，确认两个入口证书已装好，固定所选发布产物和配置。
2. 使身份服务在内部接口可用，先通过内部健康检查；这时不能假定公网 issuer 已就绪。
3. 使核心网关和 IPv4 边缘转发就绪，验证两条路线均能以正确 Host 与 SNI 到达身份服务。保留原有站点的回归检查。
4. 在确认路由可达后，按已批准计划切换业务 DNS。也可以先用受控测试解析验证路线，但不能关闭 TLS 校验或用改 Host 冒充完整的公网验证。
5. 确认公共 issuer 的 HTTPS、发现文档及返回的 issuer 一致，然后启动依赖它的 BFF。
6. 仅为已完成来源、资源、协议及访问边界审查的候选启用受保护入口，供本人逐项验收；保留原站认证并明确标为业务待验收。其他项目默认拒绝，不能因页面可达就标记业务可用。本次已按这个范围启用选定候选，完整业务仍需下一阶段验证。

systemd 的依赖顺序和进程 active 状态不等于 HTTP readiness。配置成 `After=` 并不意味着 issuer 此刻已能完成发现；应设置有界就绪检查和失败处理，不用无限重启掩盖依赖错误。

## 8. 从真实浏览器验收密码、TOTP 与注销

使用新的浏览器会话，分别经 IPv4 和 IPv6 路线执行。只记录结果、时间与安全分类，不记录密码、动态码、Cookie、token、恢复码或登录二维码。

| 场景 | 应观察到的结果 |
| --- | --- |
| 未登录访问桌面与受保护 API | 进入正确身份流程；API 无私有数据 |
| 只提供正确密码 | 不能进入受保护桌面 |
| 错误或过期 TOTP | 拒绝登录，错误不泄露账户秘密 |
| 密码与当前 TOTP 正确 | 完成双因素与 OIDC，进入本人桌面 |
| 其他已认证身份 | 仍被 owner 白名单拒绝 |
| 邮件测试与恢复 | 实际收到通知，恢复流程可完成并受保护 |
| 会话到期后的 API | 返回可处理的未认证结果，桌面显示重新登录 |
| 重放旧回调或错误 state | 拒绝建立会话 |
| 注销后重放旧平台会话 | 受保护 API 拒绝 |
| 直接访问应用入口 | 仍受网关和应用自身认证限制 |

同时检查浏览器存储与响应策略：没有身份 token；平台 Cookie 范围正确；写请求需要 CSRF 与可信 Origin；身份 Cookie 没有转发给应用。

目前本人已实际完成正确密码加 Authenticator 的公网登录，以及主动锁定后返回身份登录页并重新登录。表中缺码、错码、过期码、其他身份、恢复、旧会话重放和到期场景仍待生产验证，SMTP 实际投递也未验收。正向登录通过不等于这些负向边界全部通过。

注销还需覆盖应用本身与长连接。测试已经打开的 iframe、WebSocket、下载和后台请求；明确哪些会立即终止，哪些需要上游退出或到期。不能把桌面回到登录画面当作全部会话撤销的证据。

## 9. 每个 App 单独验收

建议用同一张表验收一个应用，再决定是否扩大其权限：

| 项目 | 通过条件 |
| --- | --- |
| 应用身份 | 页面内容符合预期项目，登记信息与真实部署一致 |
| 桌面交互 | 图标、标题、焦点、关闭、最小化、恢复与缩放正常 |
| 浏览器嵌入 | CSP、Cookie、登录跳转均按预期，不删除安全头强行通过 |
| 静态资源 | 首页实际引用的资源加载正常，无跨项目缓存污染 |
| API 与实时连接 | 固定路径、重定向、WebSocket 子协议正常 |
| 原生认证 | 原项目仍要求其自身权限，没有隐式管理员绕过 |
| 会话失效 | 过期、重新登录和注销行为已记录 |
| 网络隔离 | 不能从 App 入口代理到未登记地址或其他项目 |
| 管理动作 | 由本人选择的最小可恢复动作已验证，失败有明确反馈 |
| 两条公网路线 | IPv4 与 IPv6 分别通过，无一侧特有故障 |

iframe 不是远程桌面协议，也不会使跨来源 DOM 可随意读取。不能嵌入的应用先保留受限卡片或正式支持的替代入口。是否需要受控独立来源，应在应用登记中说明；`APP_ORIGIN` 只有审查通过后才填写。

节点、文件与任务需要另外验收：

- 节点先做只读摘要，核对数据来源、时间与节点身份，随后才开放特定服务操作。

- 任务先限定一种允许的任务，测试超时、并发、取消、重试与审计；不提供任意命令输入框连接 root。

## 10. 运维与后续扩展

**证书续期：** 先针对专属 lineage 做 renewal dry-run，核对存储参数与 hooks，不触碰旧项目。再由明确授权启用定时机制。签发证书、安装证书、验证两端、重载网关和告警是不同环节；没有 timer 和安装链路时，应如实写“尚未自动续期”。

**IPv6 变化：** 持续验证核心当前地址与 DNS 是否一致。设计受限 DDNS 时，仅允许修改规定记录，输出安全差异，并对地址歧义或来源错误停止更新。

**身份备份：** 一并备份身份数据库、需要的加密材料、恢复流程和权限说明。备份加密保存并定期做隔离恢复演练；不要把密码哈希和 TOTP 数据当作可以公开的普通配置。

**版本升级：** 固定候选制品与依赖版本，先用真实目标二进制验证配置，再选择版本并激活。保留已知可回退产物。应用回滚和身份数据迁移分别设计，避免用旧应用包覆盖新用户状态。

**服务故障：** 按 DNS、TLS、路由、身份、BFF、单应用逐层定位。保留有限时间和次数的重试，不用循环重启、关闭验证或扩大权限替代诊断。对外分享问题时只提交脱敏错误分类和复现条件。

**权限扩展：** 新 App、新节点和新写操作均默认拒绝，逐项登记和验收。若未来增加多人、共享文件或跨用户任务，先重新设计授权与隔离，再复用单用户桌面界面。

每次完成一个关卡，都在记录中注明“检查了什么”和“尚未检查什么”。只有公网双因素、两条网络路线、注销及所需应用管理动作均实际通过后，才能将对应能力标记为可用。
