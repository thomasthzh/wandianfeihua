# 同一应用的多个窗口、快速查看与分屏空间

**状态：本轮已自动发布，三项核心服务运行态复核通过，并取得下文列出的有限公网证据。** 同一应用可以拥有多个独立窗口；Finder 保存各窗口的目录偏好，图片和 PDF 使用真实文件预览，Split View 形成独立的双窗口空间。它们共同解决的是连续工作状态，尚不等同于完整 macOS。

本章沿用 `core-v6` 与 `edge-v4` 表示核心和边缘角色，不包含真实部署输入、原始日志或截图。本仓库仍是实践手册，不包含完整可启动发行包。上一阶段的文件事务、废纸篓与通知流程见[工作空间实践](17-from-windows-to-workspace-os.md)。

## 应用身份和窗口身份必须分别存在

应用标识（`appId`）对应运行状态、程序坞入口和应用切换顺序；窗口标识（`windowId`）对应具体文档、文件夹、页面、焦点和所属空间。创建第二个窗口时复用前者，分配新的后者。否则，关闭一个窗口、切换应用或从程序坞恢复时，容易误操作它的兄弟窗口。

这次将两种身份贯穿窗口创建、排列、台前调度、总览、搜索、项目输入桥和上下文菜单。窗口标题可以来自当前文件或目录；标题相同时显示可区分的后缀，标题变化不修改窗口身份。应用切换仍按应用进行，恢复时选择它的实际窗口；窗口菜单则列出具体实例。

窗口内的命令和关闭请求必须携带目标窗口标识。两个 Finder 实例各自维护目录、选择、编辑器、草稿和快速查看，不共同消费一次“保存”或“关闭”。表单的输入框、标签和错误说明也要使用实例内唯一标识；只让最外层窗口编号不同，不能解决固定表单 ID 的冲突。

退出应用采用先收集决定、再统一关闭的顺序：依次询问工作空间能够识别的未保存内容，任意取消就保留整组窗口，不在前几个窗口已关闭后才询问最后一个。确认期间若出现新的应用窗口，也要重新确认。这个协调边界不代表已经了解所有嵌入项目内部的草稿和保存协议。

## Finder 共享文件事实，保留各窗口的编辑状态

跨窗口复制与剪切使用同一主人的临时剪贴板，预览模式与真实主人分区。剪贴板只保存授权文件引用和修订，不保存文件正文；最后一个相关窗口退出时清理。移动或粘贴仍由后端核对修订和目标冲突，不因为来源是另一个窗口就覆盖现有文件。

文件创建、保存、上传、移动、撤销或放回后，同一主人的其他 Finder 窗口会重载目录和撤销摘要。重载不自动替换编辑器正文、草稿或它原来取得的修订。若另一窗口已保存同一文件，旧草稿再次保存会收到冲突提示，用户可以保留内容后决定怎样处理。

刷新整页时，按主人、预览模式和窗口标识分别恢复当前目录、列表或图标视图及排序。浏览器存储使用有版本的有限记录，验证路径、长度和枚举；不保存文件内容、未保存草稿或身份秘密。目录是否仍存在、当前会话是否有权访问，仍由服务端判断。本地偏好恢复不是跨设备同步，也不是对整个集群磁盘的授权。

## 快速查看从真实字节开始

快速查看通过受认证接口读取当前修订的文件。二进制预览沿用授权数据根、稳定文件句柄、大小与链接检查；文件名与内容签名共同决定允许的类型，不能信任上传时自报的 MIME。当前图片与 PDF 预览有明确体积上限，SVG 不作为活动文档执行。文本通过普通文本节点展示。

图片支持适合窗口、缩放、左右浏览及 Space 或 Escape 关闭。更换项目和关闭预览时取消旧请求、撤销图片对象 URL；旧请求晚到也不能覆盖新预览，或凭一条过期的未授权响应误使当前会话退出。这些交互参考了 [Apple 的快速查看指南](https://support.apple.com/guide/mac-help/preview-a-file-mh14119/mac)，本轮没有据此声称已提供标记、旋转、视频编辑或所有格式。

### PDF 白屏不能算“已经加载”

最初尝试将授权文件 Blob 放入严格隔离的浏览器 PDF 框架。框架存在、页面未报加载错误，实际截图却是白页；因此没有把该路径记成 PDF 阅读通过，也没有为消除白屏而放开脚本或同源权限。

最终改用固定的 [PDF.js 6.4.299](https://github.com/mozilla/pdf.js/releases/tag/v6.4.299)，将 Blob 直接交给本地解析与画布阅读组件。模块 worker 和资源随前端制品自托管，不接收外部 PDF URL，不依赖公网 CDN；支持分页、缩放与适合窗口。没有实例化脚本管理器、链接动作或活动注释层，并限制文件、页数和画布分配。切换文档或关闭时销毁对应的加载任务、文档和 worker。

中文 PDF 还需要正确的字符映射。本轮补入本地 CMap 等配套资源，并核对中文样本实际可读；英文单页成功不能替代这一步。构建同时保留四份相关许可文本，核对它们进入制品，不能只复制运行脚本而漏掉附带资源的许可。上游许可参见 [PDF.js 许可文件](https://github.com/mozilla/pdf.js/blob/v6.4.299/LICENSE)。

## Split View 是一份空间关系

左右平铺只安排两个矩形。Split View 还需要保存两个具体窗口的成员关系、比例、各自返回的普通桌面和浮动几何。它应成为独立空间，而不是临时把两个应用标识绑在一起。

本轮提供以下连贯路径，参考 [Apple 当前 macOS 27 的 Split View 指南](https://support.apple.com/guide/mac-help/use-apps-in-split-view-mchl4fbe2921/mac)：

1. 从窗口布局菜单选择一侧，再选择另一个真实窗口；同一应用的两个窗口也可以组成分屏。
2. 拖动或用键盘调整分隔条，限制两侧的最小宽度，并保存比例。
3. 通过菜单或拖动标题到另一侧交换位置；替换其中一侧时保留另一窗口和空间关系。
4. 将一侧移回桌面、转为独立全屏，或退出整组，分别恢复原来的返回位置。
5. 在调度中心把窗口拖入另一个单窗口全屏空间，创建真正的双窗口空间；已有双窗口空间不接收第三个成员。

标题拖动在松手时再次核对实际配对和比例，防止把手势开始时的旧关系提交到已改变的空间。取消、失去焦点、调整视口、认证失效与卸载都要释放捕获并清理手势；回到拖动阈值内时也清除旧预览。换边高亮和拖动提示使用随窗口顺序计算的图层，避免长会话中被越来越靠前的窗口盖住。

### 鼠标真正命中了什么

这轮还遇到事件命中问题：外层窗口图层使用 `pointer-events: none`，让空白处能够操作桌面；新增交互层如果没有明确恢复命中，就可能看得见却点不到。修正时只对需要交互的层恢复 `pointer-events: auto`，不把整个遮罩变成无边界的点击拦截层。之后用真实鼠标重新检查选择、拖动和退出，而不是只检查按钮是否出现在页面结构中。

## 从修复到可审查的自动发布

先完成实现和独立审查，再冻结同一份源码，构建前后核对它与制品的对应关系。测试、资源、worker、字符映射和许可都属于制品的一部分；修复白屏后应重验实际正文，修复事件命中后应重验真实鼠标。

自动发布只执行已审入口：核对当前基线、制品、配置和受保护输入，失败时区分能够证明的自身变动与未知并发变动；不能为“恢复成功”覆盖未知内容。发布后再核对实际服务、匿名认证边界和真实会话。沿用既有密码、Authenticator 与服务端钥匙串，减少重复复制命令，不把自动提权等同于可以任意修改宿主系统。
