# 运维流程：从准备材料到公网验收

这份流程使用示例入口 `os.example.net` 与身份入口 `auth.os.example.net`，以 `core-v6` 和 `edge-v4` 表示两个节点角色。它描述实施顺序与验收边界，不是可以直接复制执行的部署脚本。本仓库的公开材料也不等于完整桌面源码或现成的一键部署包。

早期配置曾完成独立网关升级与四阶段校验；新候选首轮本人发布因 BFF 的 `INVALID_NODE_ENV` 停止。之后本人受控恢复时，环境已规范且未修改，重校验及激活自动检查通过。核心、边缘与业务 DNS 已启用；本人公网正向双因素登录、主动锁定重登，以及部分桌面、节点、文件和任务操作已验证。负向认证、SMTP 实际投递、完整注销、独立外部 IPv6 与应用业务仍待验收。

## 先定义每个阶段的完成条件

| 阶段 | 完成条件 | 这一阶段不自动执行的动作 |
| --- | --- | --- |
| 本地桌面 | 登录、窗口、启动器与基本交互能够演示 | 公网发布与远程管理 |
| 项目核查 | 确认真实入口、协议、原站身份和嵌入限制 | 将健康检查页标成完整应用 |
| 文件准备 | 来源、版本、权限和回滚材料核对通过 | 选择发布版本或启动服务 |
| 身份准备 | 唯一所有者、密码、TOTP、生产 OIDC 配置齐备 | 自动扩大应用权限 |
| TLS 准备 | 演练、正式证书、链、域名范围及密钥匹配检查通过 | 启用 DNS 或替换已有业务网关 |
| 生产校验 | 后端、证书、身份服务和新网关分别通过 | 宣称公网已经就绪 |
| 明确启用 | 选定发布、启动所需服务，按来源与边界审查结果启用受保护候选入口与 DNS | 把候选页面可达标为业务已通过，或开放未审查项目 |
| 外网验收 | 从独立 IPv4、IPv6 网络完成身份与业务测试 | 以单次成功代替后续运行维护 |

阶段工具应尽可能合并，减少使用者反复输入命令。每次本人提权执行之前，要能看清具体变更范围；执行过程中应有分阶段结果。需要交互输入的秘密留在本人终端内，准备、检查和启用仍保留清楚的停点。

本次发布已采用单次本人提权入口：核验候选与已有材料，检查各组件；只有全部通过才选择版本、按依赖启动并汇总结果。首轮触发失败停点，恢复入口在同一次执行中给出固定分类、只在已知问题时修正并重校验。本人恢复时无需修改规范环境，重校验通过后完成了激活。已经完成的身份和证书没有重新初始化。恢复工具的 7 项测试、相同 Linux 可执行文件合成检查、本人恢复结果分别记录，不能相互替代。

## 准备独立的生产组件

`edge-v4` 承接 IPv4，`core-v6` 承接 IPv6，并通过 Tailscale 连接。两条浏览器路径应抵达相同的身份策略和固定应用路由。已有网关继续服务原有业务；新系统采用独立配置、账户、状态目录和可执行文件，避免把一次新项目部署变成整台服务器的迁移。

在每个实际运行节点核对可执行文件的版本与模块，再使用该文件检查该节点的配置。跨机器验证可以帮助提前发现问题，不能替代目标机器上的验证。构建记录中记录过由此漏掉旧版 Caddy 的经历。

准备新项目文件时，应拒绝未知目标、意外软链接、不合适的权限以及未经审查的覆盖。公开来源文件经过核对后形成受管理快照；服务配置由 root 管理，服务进程只获得自身必需的读取权限。已有人工填写的值应当保留；不匹配时报告并停止，而不是猜测新的值覆盖进去。

## 让生产身份形成单独边界

生产入口使用密码和 Authenticator TOTP，桌面后端通过 OIDC 验证身份并限定唯一所有者。桌面的公开来源、身份发行者和回调地址应当固定。网关放行不代替后端验证，后端会话也不接受本地演示登录作为备用路线。

已有绑定的迁移由所有者明确执行。迁移工具仅处理此次新系统需要的身份字段，拒绝覆盖未知用户库或已有状态，完成后清理受控暂存。恢复材料应另行妥善保存，不能放进仓库、聊天或普通操作报告。

开启应用时保留原站身份。某些应用仍需自身账号或控制器授权，不能为了获得看似流畅的单点登录而拆掉原保护。

## DNS 先做只读计划

先读取授权范围内的记录，生成待审阅计划。计划应包含精确名称、期望 A/AAAA、现有记录冲突、通配匹配变化和未选择应用可能受到的影响，不包含凭据、控制面身份或不必要的私有字段。

动态 IPv6 需要在执行现场重新发现。只接受明确、唯一、仍首选的非临时全球地址；有歧义便停止。网关的精确绑定与拟发布 AAAA 应一致，地址变化后的同步与验证属于持续运维工作。

同名 CNAME 与 A/AAAA 的冲突要先人工核对归属；多条、未知类型或委派不应被工具盲目删除。建立精确桌面节点还可能改变下级应用对上层通配记录的继承，不能只看桌面名称本身是否解析成功。相关故障与依据见[DNS 排查](05-troubleshooting.md#新增桌面记录后其他应用解析改变)。

只读计划不执行变更，也不是未来可直接执行的状态快照。实际写入放在明确的发布阶段，执行前重新核对记录及当前地址，避免每一条记录都拆成一次来回操作。

## 证书分成签发、安装和续期三件事

先用独立的 staging 配置、工作目录和日志目录演练，再明确进行生产签发。不要让新项目隐式继承其他项目的 ACME 配置、凭据或自动 hook。失败后保留账号与现场，按协议证据决定恢复方式。

正式签发完成后，还需要验证有效期、公开信任链、精确域名范围和密钥匹配，再安装到服务账户可读取的位置。签发成功并不会自动完成两个入口的安装。

本次实施采用接收方临时公钥加密传输材料，并通过可信通道核对密文摘要。私钥明文不经过普通中转文件或聊天。接收端只有在认证解密成功后才解析内存中的内容，随后再次检查目标、证书范围、链和密钥对应关系。

证书和私钥是一组文件。单个文件的原子替换不等于整组更新已经原子完成；应在新服务停服的准备阶段完成更换，第二步或持久化确认失败时恢复原组。未知旧文件拒绝覆盖，受控备份与非敏感结果记录用于恢复。

续期还需要将新证书重新部署到两个入口并验证。ACME 续期成功不能证明网关已经加载了新文件。这条完整更新链路仍须通过实际演练。

## 分阶段执行真实校验

校验前确认新系统的相关服务已经停止，服务状态明确为已加载且停止或失败；正在启动、正在停止或无法确认状态时不要继续。校验必须以实际服务身份运行，环境只来自严格解析的新项目配置，不执行环境文件中的文本。

四个阶段分别检查：

1. **生产后端**：配置与身份文件可读取，前端构建位置正确；检查模式不做 OIDC discovery、不创建监听或会话。
2. **公开证书**：证书当前有效，桌面和身份域名匹配；安装阶段已经另行完成链与密钥检查。
3. **Authelia**：使用实际固定版本与原配置执行验证，确认模板、身份和通知设置能够解析。
4. **Caddy**：以新网关服务身份加载专用状态目录，对实际配置完成验证。

每个阶段输出成功、失败、环境输入不合格或超时，以及有限的已知分类。一个阶段失败时，能够独立执行的其他阶段继续，方便一次操作拿到完整结果；总体结果保持未完成。原始输出只在本机内存中分类，不能把带环境内容的渲染配置或原始错误直接上传。

Caddy 的 `validate` 会加载并 provision 模块，检查强于单纯 `adapt`，但不会启动配置；模块也可能占用独占资源。因此它需要放在适合该服务状态的流程里，不能被当成纯文本解析。[Caddy 命令文档](https://caddyserver.com/docs/command-line#caddy-validate)

首轮 `NODE_ENV` 拒绝不能被历史通过记录抹去。有限分类、已知问题修复与重校验应先于续行；规范值不改、未知形式保留现场停止。本次恢复确认环境规范且未改值，初次原因不能唯一归因；合成引号错误只是复现条件，详见[排错记录](05-troubleshooting.md#bff-曾拒绝-node_env恢复时未修改现场变量)。

## 明确启用顺序与回退点

所有准备检查通过后，才进入实际发布。需要先让身份服务及其 HTTPS 入口可用，再启动依赖该入口完成 OIDC discovery 的生产桌面后端。否则会出现后端等待身份入口、身份入口又等待后端的循环。

IPv4 边缘的已有网关采用精确站点追加：临时组合配置先检查，保留原文件及既有业务路由，再在明确启用阶段应用新增入口。不能用一个新的通配监听抢占已有业务。

每个启用动作都应有对应回退：新发布回退至已知旧版本；新增入口撤回本次追加部分；证书更新恢复已知旧组；二进制升级恢复受控旧文件。回退范围应限于本次新系统，避免顺带重置其他业务。

## 公网验收必须覆盖真实业务

从不依赖 Tailscale 的 IPv4、IPv6 网络分别验收浏览器证书和身份流程：未登录、仅有密码、错误动态码均不能进入受保护工作区；完整验证后才获得桌面会话。还要测试直接访问源站、伪造转发头、跨来源写入与会话过期，确认没有旁路。

应用按项开放，每项都需要检查窗口内原站登录、刷新、跳转、实际授权管理操作、WebSocket/SSE、上传、下载和退出。HTTP 成功或窗口能显示登录页，只能算其中一条证据。

本人已验证公网密码加 Authenticator 正向登录、主动锁定返回身份登录页并重新登录；窗口总览搜索、键盘恢复焦点和左右并排也已验证。实际核心与 Tailnet 状态、授权文件创建编辑及刷新回读、扫描结果和刷新后任务保留通过。这些结果不覆盖错误动态码、SMTP、任务取消、服务重启恢复或跨应用注销。四个候选已加载原站登录、设置或工作区选择页面，原站业务继续单独验收。

同一站点体系下的不同来源仍需精确的浏览器来源检查，不能仅依赖 Cookie 或双因素网关。WebSocket 的浏览器握手携带 Origin，服务端应按自身策略核验；连接建立后的撤销还需要另外设计。[WebSocket 协议](https://www.rfc-editor.org/rfc/rfc6455#section-4.1)

平台注销、身份门户注销、原站会话注销和现有长连接撤销必须分开记录。节点、文件和固定任务已接真实后端并完成上述本人生产验证，仍需扩大权限前的测试和恢复验收。当前不能承诺完整集群操作系统或所有应用的一次登录与一次退出。
